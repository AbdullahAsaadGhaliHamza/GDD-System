## Game Overview

<!-- status: done | owner: Sam Torres | updated: 2025-01-10 -->

**Echo Veil** is a hand-painted 2.5D puzzle-platformer set inside the collapsing memory palace of a woman who cannot remember who she is. Players navigate crumbling rooms, manipulate echoes of past events, and piece together a fragmented identity before the palace falls.

| Field | Value |
|-------|-------|
| Genre | Puzzle-platformer, atmospheric |
| Platform | PC, Nintendo Switch |
| Engine | Godot 4.3 |
| Target rating | E10+ |
| Expected playtime | 6-8 hours |
| Monetization | Premium (one-time purchase) |
| Comparable titles | Limbo, Gris, A Short Hike |

### Elevator Pitch

> A puzzle-platformer set inside a collapsing memory palace. Manipulate echoes of the past to rebuild the present.

### Player Fantasy

The player should feel like a careful archaeologist excavating emotional ruins — each solved puzzle a recovered memory, each completed room a small act of reconstruction.

## Core Game Loop

<!-- status: done | owner: Sam Torres | updated: 2025-01-10 -->

```
Enter room
  └─ Observe environment and echo fragments
       └─ Manipulate echoes (place, rewind, combine)
            └─ Solve the environmental puzzle
                 └─ Unlock path forward + recover memory fragment
                      └─ Story beat plays
                           └─ Enter next room
```

### Loop Breakdown

**Micro loop (30 seconds - 3 minutes)**
Observe a single puzzle element, experiment with echo placement, find the solution.

**Mid loop (5-15 minutes)**
Complete a room or corridor sequence, recover a memory fragment, understand a piece of the protagonist's story.

**Macro loop (full playthrough)**
Reconstruct the protagonist's identity, reach the palace's core, and make the final choice.

### Session Length

Target session: 25-40 minutes. Save points between every room. No mid-room saves — rooms are short enough that this should not frustrate players.

## Design Pillars

<!-- status: done | owner: Sam Torres | updated: 2025-01-10 -->

These three pillars govern every design decision. When two design options conflict, the pillar order below acts as a tiebreaker.

### 1. Clarity over complexity

Every mechanic must be learnable by watching, not by reading. If a player needs a tutorial popup to understand a new element, the environment is not communicating clearly enough. Add visual affordances, revise the geometry, or cut the mechanic.

**Applies to:** puzzle design, UI, new mechanic introductions, level layout.

### 2. Emotion before challenge

Difficulty exists to create meaning, not frustration. Puzzles should feel satisfying to solve, not clever traps. If playtest data shows average solve time exceeding 8 minutes on a single puzzle, redesign the puzzle, not the player.

**Applies to:** difficulty tuning, puzzle design, death/fail states.

### 3. World coherence

Every element in the environment must feel like it belongs to the memory palace. No floating UI elements without diegetic justification. Music reacts to the protagonist's emotional state. Props reflect the memories they protect.

**Applies to:** art direction, audio, UI design, level dressing.

## Mechanics & Systems

<!-- status: in_progress | owner: Priya Nair | updated: 2025-01-12 -->

### Echo System

<!-- feature_status: in_progress | milestone: M1 | priority: critical -->

The core mechanic. Every room contains "echoes" — translucent recordings of past events in the memory palace. Players can:

| Action | Input | Status |
|--------|-------|--------|
| Pick up an echo | Interact button | `~ in_progress` |
| Place an echo | Interact button (held location) | `~ in_progress` |
| Rewind an echo | R button | `o planned` |
| Combine two echoes | Drag onto each other | `o planned` |
| Dismiss an echo | Double-tap dismiss | `+ done` |

**Design note:** Echoes are not time travel. They are recordings that play on loop. The player is choosing *where* and *when* in the loop to place them, not controlling the past.

**Open question:** Should echoes have a "weight limit" — can the player hold more than one at a time? Current prototype: one at a time. Playtesting will determine if this is too restrictive.

### Movement

<!-- feature_status: done | milestone: M1 | priority: critical -->

Standard 2D platformer movement. No double jump — the protagonist is not athletic. Intentionally limited.

| Stat | Value | Status |
|------|-------|--------|
| Walk speed | 180 px/s | `+ done` |
| Run speed | 280 px/s (hold sprint) | `+ done` |
| Jump height | 96 px | `+ done` |
| Coyote time | 80ms | `+ done` |
| Jump buffer | 100ms | `+ done` |

### Memory Fragment System

<!-- feature_status: in_progress | milestone: M1 | priority: high -->

Fragments are collectibles that also advance the story. Collecting all fragments in a chapter unlocks an optional "complete memory" cutscene.

- Fragments per chapter: 8-12
- Types: visual (image), audio (voiceover), written (journal entry)
- Stored in the Memory Viewer menu (see UI section)
- `~ in_progress` — fragment collection and storage working, viewer UI not started

### Fail States

<!-- feature_status: planned | milestone: M2 | priority: medium -->

Death is not a mechanic. The protagonist cannot die. If the player reaches an impossible state (puzzle locked, trapped in geometry), the game detects this after 30 seconds of no input progress and offers a soft-reset to the room entrance with no penalty.

`o planned` — detection logic not yet designed.

### Level Design Rules

1. Every room must be solvable by a player who has never failed it before.
2. No puzzle requires precise timing under 500ms windows.
3. Every room has exactly one solution, but players may discover it multiple ways.
4. The solution must always be visible in the starting position of the room.

## Narrative & World

<!-- status: in_progress | owner: Lena Booth | updated: 2025-01-13 -->

### Premise

The protagonist, **Mara**, wakes inside a vast palace made of her own memories. She cannot remember who she is, only that something was taken from her. As she navigates the collapsing rooms, she recovers fragments of a life: a daughter, a promise, a loss. The palace is not a metaphor — it is literally how Mara processes memory. She has been here before.

### Tone

- Melancholy without being hopeless.
- Quiet tension, not jump scares.
- Moments of genuine warmth inside the grief.
- Referencing: *Eternal Sunshine of the Spotless Mind*, *What Remains of Edith Finch*.

### Characters

### Story Beats

|------|---------|------|--------|
| Opening — Mara wakes | 1 | Cutscene | `+ done` |

| The Echo speaks for the first time | 1 | Voiced dialogue | `~ in_progress` |

| Ending A — Mara lets go | 5 | Cutscene | `o planned` |
| Ending B — Mara holds on | 5 | Cutscene | `o planned` |

### World Rules

1. The palace exists only in Mara's mind. Physics obey memory logic, not gravity logic.
2. Rooms decay as memories weaken. Solved rooms stabilize.
3. Echoes are exact recordings, not interpretations. They cannot lie.
4. The Echo (character) can rewrite echoes. This is the source of conflict.

## Art Direction

<!-- status: in_progress | owner: Jesper Vang | updated: 2025-01-11 -->

### Visual Style

Hand-painted 2.5D. Backgrounds are layered painted environments. Characters and interactive elements are clean vector-adjacent 2D sprites composited over painted layers.

**Color palette:**
- Stable rooms: desaturated blues and greens with warm amber light sources.
- Decaying rooms: cooler, higher contrast, grey-purple shadow tones.
- Echoes: soft luminescent teal with slight motion blur.
- Memory fragments: warm gold, stand out against all environments.

## UI / UX

<!-- status: planned | owner: Sam Torres | updated: 2025-01-10 -->

### UI Philosophy

Diegetic where possible. Every UI element should look like it belongs to the memory palace. Avoid standard game UI conventions where a palace-native alternative exists.

| UI Element | Approach | Status |
|------------|----------|--------|
| Health / death | Not applicable — no death | N/A |
| Pause menu | Manifests as the palace "pausing" — room freezes | `o planned` |
| Memory Viewer | Physical journal in Mara's hand | `o planned` |
| Settings | Only accessible from main menu | `o planned` |
| Subtitles | Standard placement, adjustable size | `o planned` |
| Chapter title card | Handwritten style, fades in on chapter start | `o planned` |

### Menus

- Main menu: Atmospheric single screen, no music until player interacts.
- No loading screen tips. Loading screens show a room sketch from the upcoming chapter.
- Continue / New Game / Options / Credits. No achievements screen in-game (platform-native).

### UX Flows

```
Main Menu
  ├─ Continue (last save)
  ├─ New Game ──► Chapter Select (unlocked chapters) ──► Room 1
  ├─ Options ──► Audio / Visual / Accessibility / Controls
  └─ Credits

In-Game
  ├─ Pause ──► Resume / Options / Main Menu / Quit
  └─ Memory Viewer ──► Fragments (visual / audio / text)
```

### Echo System — Technical Spec

The echo recording system stores a circular buffer of the last 10 seconds of an entity's state at 24 samples/second. Each sample stores:

```
position: Vector2
animation_frame: int
facing: int (-1 or 1)
custom_state: Dictionary  # entity-specific data
```

Buffer size per echo: ~240 samples max. Memory footprint per active echo: estimated 4-8 KB depending on custom_state complexity.

Max simultaneous active echoes: 4 (design constraint, also a performance constraint).

### Save Format

```json
{
  "schema": "1.0",
  "playtime_seconds": 3820,
  "current_chapter": 2,
  "current_room": "2-03",
  "fragments_collected": ["1-01-A", "1-02-B", "1-03-A"],
  "rooms_solved": ["1-01", "1-02", "1-03", "1-04"],
  "settings": {
    "audio_master": 1.0,
    "subtitles": true,
    "colorblind_mode": "none"
  }
}
```
